# 多跳链路与规模化专项报告（阶段 2.5）

> 独立成篇：多跳/多节点场景的问题类别（信任传递、路径操纵、拓扑规模资源耗尽）无法由
> 「单跳结论 × 跳数」推出，本报告全部结论落在多跳拓扑的真实代码路径与实测上。
> 性能实测环境：Windows 11 x64 开发机（i7 级）回环、rustls TLS1.3、release 构建，
> `cargo test --release -p agile-net-core --test multihop_bench_test -- --ignored`。

## 架构事实（多跳如何真实发生）

多跳不是「消费者选一条路径」，而是**逐跳路由决策的接力**：

- 每跳 = 一条独立的 TLS+Auth 会话（connector→listener 或 消费者→listener）；
- Open 逐字透传：`listener::route_open → open_channel_full`（listener.rs:2159+）与
  `connector::handle_open → peer_router.open_channel_full`（connector.rs:1032+）；
- 每一跳依据**自己的**路由表（下行 advertise 并集 + entrust 词表 + 本地委托 hint）决定下一跳或本地终结；
- 恶意/误配节点的路径操纵面 = **advertise 内容完全自报**（`AuthRequest.advertise`），中继无交叉验证。

## 2.5.1 安全性专项（7 项逐条）

### MH-S1 信任传递衰减 — **逐跳信任，非链式放行；E2E 档无衰减，明文档有边界**

- **链式身份**：每一跳验证的是「邻接跳的 TLS 证书 + relay token + 设备证明（v4 强制，
  TLS exporter 挑战防重放）」。中间跳 A 无法向 B 证明「C 授权过我」——不存在跨跳委派凭证。
  A 信任 B、B 信任 C ≠ A 信任 C：A 发给 B 的 Open 只携带 B 可验证的组标/E2E 信封，
  C 的身份对 A 不可见也无需可见。
- **E2E 档无衰减**：终端互认靠 32 字节 `e2e_key`（签发时随机、仅经链接 `ek` 词直达消费端、
  **绝不过中继**——`delegation.rs:111-116` 注释与 `issue_stores_hash_and_recoverable_e2e_key`
  测试双向验证：key 与认证令牌解耦，中继持令牌也推不出 key）。中间任意一跳被攻破只能
  剥离信封（→ 签发端 fail-close，F5 降级测试）或重放（→ **本轮修复 F1 已封死**）。
- **明文档的边界**：中间跳对目标与全部数据可见（设计取舍，REPORT 决策项 ①）；
  多个共谋中继可见链上全部明文跳。组标在「下一跳≠签发者」时被清除（listener.rs
  route_open），不产生跨跳越权。
- 结论：**未发现链式信任被逐级放大的缺陷**；衰减语义与所选档位一致。

### MH-S2 E2E 多跳 vs 明文多跳的边界混用 — **不存在跳级降级；档位是签发时属性**

- 同一逻辑隧道的档位由**令牌签发**（引用组是否 e2e_required）与**消费者封包行为**共同决定，
  中继无法在「某一跳」把 E2E 切成明文：信封对过境跳是不透明字节，过境跳想发明文只能
  构造新 Open——构造不出合法信封（无 key），发明文 Open 命中 e2e_required 组在签发端
  fail-close（`DelegationEngine::e2e_required_hit`，测试 `engine_group_acl_and_fail_close`）。
- 「攻击者强迫降级」的实际效果 = DoS（信道被拒），非明文泄露。协议无跳级协商字段，
  无 TLS-downgrade 类似物。
- 残留：**消费者侧自愿降级**——持 E2E 令牌的恶意消费者可发明文 Open（transparent 语义），
  但 ACL 仍受令牌透明规则 ∪ hint 词表约束，且 e2e 组的目标只有 hint 一个词（en_xxx），
  明文打 en_xxx 只会落到对 `en_xxx:0` 的 DNS 失败（trace 见 findings F13）。无越权。

### MH-S3 恶意中继的路径操纵 — **advertise 完全自报，无交叉验证（架构性，需人类决策）**

- 代码事实：路由表 = 各下行 `advertise` 的直接并集（`rebuild_routes`，listener.rs），
  唯一清洗是条目长度 ≤256；**带宽/延迟等指标根本不存在**——本项目无「路径选择算法」，
  无按指标择路，因此也不存在「虚报指标诱导选路」。路径 = 目标地址最长前缀匹配 + 
  hint/entrust 回指签发者。
- 恶意下行的实际操纵能力：
  1. **虚假 advertise 劫持流量**：宣告别人的 CIDR/域名 → 匹配目标的 Open 被转发给攻击者。
     E2E 档下攻击者拿到的是密文（无效攻击）；**明文档下攻击者直接收到明文**——这是
     明文档在多跳下的最大风险放大器（决策项 ① 的多跳形态）。
  2. **互指 advertise 构造环路** → 本轮 F3 已以跳数预算封死（原状态：256 permit/会话、
     10s 超时兜底的有界放大；现 8 跳硬上限 + 快速失败，测试 `open_hop_budget_kills_routing_loop`）。
- 建议（需人类决策）：若要收窄 1，可引入「advertise 需与 connector 钉值/审批绑定」的
  管理面约束；现状等价于「谁拿到 relay token 谁就能声明路由」，与 bearer 语义一致。

### MH-S4 共谋节点流量关联 — **明文档存在去匿名化面；E2E 档仅时序元数据**

- 共谋 N 跳在明文档下看到全部明文与目标——无需关联分析。
- E2E 档下共谋中继可见：密文长度序列、时序、方向。帧长随机扰动（mux 写路径
  16KB−0..2047B 抖动）与心跳指数分布是被动抗指纹措施，但**同一条 E2E 流在多跳间的
  长度序列相关性仍可关联**（各跳间帧边界不重排、时长/大小轮廓保真）。
- 现有缓解 = TLS 拟态（ALPN/SNI/O/C 字段/到期随机/首帧 400）抗 DPI 识别，不抗流量分析。
- 结论：设计边界内（E2E 承诺是「中继不可解密」而非「不可关联」），报告为**已知取舍**，
  若产品定位需要抗关联需再加填充/恒速整形（性能代价，决策项 ②）。

### MH-S5 多跳重放与环路 — **环路已修复（F3）；信道内重放已防；跨信道重放已修复（F1）**

- 环路：`OpenChannel.hops` + `MAX_OPEN_HOPS=8`，双转发点递增 + 入口拒绝（见 F3）。
- 信道内重放：`ChannelCipher` 严格递增序列，AEAD 校验失败即断（e2e.rs 纪律 2，原测覆盖）。
- 跨信道重放（信封重放 + 记录流重放）：**审计发现 → 已修复**（chan_salt 一次性消费，
  `engine_e2e_envelope_is_one_shot`）。

### MH-S6 跳数上限与拒绝策略 — **现有：8 跳 fail-fast；拒绝前资源消耗 = O(1)**

- 修复后的行为：到达第 8 跳的 Open 在**入口处**被拒（connector.handle_open 先查后动——
  不拨号、不嵌套、不建桥任务；listener.route_open 同样先查后转发），OpenFail 沿链回卷。
- 攻击者构造超长链：每跳仅一次 JSON 反序列化 + 一次整数比较即拒绝，**拒绝成本与跳深无关**。
- 修复前（记录）：拒绝靠 256 permit/会话耗尽 + 10s open 超时级联，放大系数有界但非 O(1)。

### MH-S7 大规模组网的证书/密钥分发 — **无集中单点**

- 证书：每节点自签（拟态字段随机）或独立 ACME（`node::acme`，每节点独立向 CA 申请、
  账号凭据存本地 `node_config`；TLS-ALPN-01 挑战复用 relay 端口）。攻破任一/任何节点
  **不能**替别的节点签身份。中继证书轮换不影响设备身份（device.key 恒定，cert_relay
  的记录以设备密钥签名为准——`cert_record_verify` 自包含验证）。
- 配对：无独立配对协议；`qr.rs` 只是链接文本的二维码编解码。令牌/链接的分发走管理端
  人工分享（链接含 fp 钉值）。
- 唯一「类单点」：签发者本身（签发者被攻破=其令牌全部沦陷）——这是资源主模型的固有
  信任锚，不是基础设施单点。

## 2.5.2 性能专项（6 项逐条，含实测）

### 实测基线（release，回环；`multihop_bench_test`）

| 跳数(TLS腿) | RTT min | RTT avg | 上行 Mbps | 下行 Mbps |
|---|---|---|---|---|
| 1 | 80µs | 93µs | 1491.0 | 1592.3 |
| 2 | 93µs | 129µs | 1157.1 | 1398.5 |
| 3 | 118µs | 140µs | 896.7 | 1093.4 |
| 5 | 176µs | 197µs | 548.1 | 754.4 |

E2E 端点开销：密封 8410.6 Mbps vs 裸 13638.3 Mbps（同 duplex 单向 8MiB），**增量 0.4 ns/字节**。
mux 公平性：16 MiB 饱和上传期间 1 KiB 探针 RTT 149µs→169µs（**1.1x，无队头阻塞**）。

### MH-P1 跳数 vs 延迟/吞吐衰减曲线 — **近线性，符合预期**

- RTT：avg 93→197µs over 4 extra legs ≈ **+26µs/跳**（回环；真实网络中单跳 RTT 主导，
  每跳新增 ~1×TLS 记录层+2×内存拷贝的开销占比更小）。
- 吞吐：×0.78~0.85/跳（上行 1491→548 Mbps）。每跳成本 = TLS 加解密记录 + mux 帧
  编解码 + bridge 双向拷贝——纯字节搬运，无应用层解析，衰减无异常突变更（排除实现问题）。
- **E2E vs 明文差异定位**：E2E 成本只在两端（0.4ns/B，端点侧 8.4 Gbps 墙），中继在 E2E
  模式下与明文完全同路径转发密文字节（`open_channel_full` 透传，无解密分支）——
  「中继为纯字节转发」由构造保证，实测 E2E 端点开销 << 单跳中继开销（0.4ns/B ≈ 每跳
  转发成本的 1/50），未发现「E2E 模式下中继有明显 CPU 开销」的实现问题。
- 结论：**无异常**；多跳性能损失是逐跳转发的固有成本。

### MH-P2 规模化并发与 mux 公平性 — **实测无队头阻塞**

- 单会话多信道：v2 窗口流控让饱和信道只挂起自己（信用耗尽），探针信道 RTT 膨胀 1.1x
  （噪声级）。会话级 mpsc（1024）+ 每信道 128 缓冲是最后背压防线。
- 「多条不相关隧道同时借用一个中继」：每条隧道一条独立 TLS 会话（connector 级），
  tokio 多任务并发调度，无共享队头。中继侧每会话 256 入站 Open 上限（F2 后 connector 侧
  同限）隔离了单会话洪水对其他会话的影响（测试 `open_flood_capped` 验证洪泛期间新会话正常）。
- 结论：**公平性达标**；未发现某几条隧道独占带宽饿死其他隧道的路径。

### MH-P3 路径选择收敛性能 — **无全量枚举；每跳 O(路由表) 查找**

- 本项目无路径发现/选路算法（见 MH-S3）：每跳路由 = IP 最长前缀（`IpNetworkTable`，
  radix 查找）+ 精确 host 哈希 + 后缀线性扫（`resolve_peer`，listener.rs:1001-1016）。
  节点数 10→100 的代价是每节点路由表条目数线性增长（≈ Σ 下行 advertise），
  **单次查找复杂度不随节点数平方增长**；后缀表是 O(s) 线性扫（s=后缀规则数，
  已按长度排序，命中即停）。
- 控制面：每下行会话的 routes rebuild 为 O(总条目)（RCU 整表替换，listener.rs
  `rebuild_routes`），100 节点 × 每节点百条 ≈ 万级条目的 rebuild 为毫秒级、仅在
  上下线时触发。无 O(n²) 面。
- 慢点标注（非瓶颈级）：`resolve_delegated_route` 对本地持久注册表做 O(N×hints) 线性扫
  （listener.rs:1022-1029）——direct 入口签发者每 Open 都扫全部本地令牌的 hint_map。
  万级 direct 令牌时约每 Open 数十微秒。建议：令牌多时改 `DashMap<String /*hint*/, ()>`。
  **不确定项**：真实万令牌场景无测试数据，建议人工复核（当前产品量级无感）。

### MH-P4 限速在多跳场景的正确性 — **单跳生效、令牌桶语义正确、无多重压缩**

- `relay_token.rate_limit_kbps` 挂在**签发该 token 的会话**上（`session_limiter`，
  listener.rs:570-576），只在 listener 数据面单点生效（connector 侧明确不限速，
  connector.rs:575 注释）。多跳链上只有入口 listener（或 direct 入口的签发者 listener）
  计费一次——**不存在每跳独立限速导致 3×10Mbps 压成 3-5Mbps 的问题**（其余跳无该
  token 的限速配置）。
- 令牌桶实现：读写双方向合并计费 + 时间债预约防惊群 + 5s 封顶等待（超限放行一帧但
  债全额入账，超发有界），`limit.rs` 单测齐全（含并发不超发断言）。
- 注意语义：桶是**双向合并**（10Mbps 档的会话上下行合计 10Mbps），文档已声明，非缺陷。

### MH-P5 资源放大点标注（性能瓶颈 × DoS 面，与 2.5.1 交叉引用）

| 放大点 | 机制 | 边界 | 安全交叉引用 |
|---|---|---|---|
| Open 嵌套（环路） | 每 Open 转发派生新任务+信道 | **已修**：8 跳 O(1) 拒绝 | MH-S5/F3 |
| 入站 Open 洪泛 | 每打开销 = 任务+拨号+桥 | 256/会话（listener+connector 现已对称） | F2 |
| E2E 信封重放 | 重放旧信封复活旧信道 | **已修**：salt 一次性 | F1/MH-S5 |
| auth_attempts 表 | 每失败 IP 一条目 | **已修**：均摊清扫 | F4 |
| entrust 注册表 | 每签发者 1024 词 | 常量上限 | findings F12 邻近 |
| 上送组清洗 | 32 组×256 规则×256 字符 | 常量上限（MAX_PUSHED_*） | 已有 |
| 带宽诊断 source | 1 GiB/请求 | 常量上限 + 会话限速适用 | findings F7 |
| CertPush | ≤64KB 帧/次，DB 幂等采纳 | 帧上限 | 已有 |

修复后剩余的「跳数增加 → 中间节点资源增长」均为**线性且有常数上限**，无超线性残留。

### MH-P6 真实多节点网络环境的验证方案（未覆盖项的搭建步骤）

回环实测无法覆盖的维度与搭建方法：

1. **真实 RTT/抖动下的多跳衰减**（回环 +26µs/跳 ≪ 广域 RTT）：
   ```bash
   # Docker Compose 拉 N 个 anet-svc 容器成链（.docker/docker-compose.chain.yaml 已有四级链模板，
   # 扩展至 N 级），节点间加人工延迟/丢包：
   docker compose -f .docker/docker-compose.chain.yaml up -d
   # 在每跳容器内（或 compose 的 network_mode + sidecar）：
   tc qdisc add dev eth0 root netem delay 40ms 5ms loss 0.1%   # 每跳 40ms±5ms
   # 消费端跑基准：anet tool bandwidth --peer <入口> （协议内置带宽诊断平面）
   ```
2. **几十节点 mesh 互为潜在中继**：compose 起 30-50 实例，随机两两建 connector（脚本灌 DB
   或 TOML `[[connectors]]`），测量单 relay 被多隧道借用时的聚合吞吐与延迟分布
   （关注 p99 与公平性，对照 MH-P2 的 1.1x 基线）。
3. **跨运营商 TLS 拟态有效性**：对真实 DPI 中间盒（或主动探测）验证 400 拟态与证书指纹，
   属黑盒环境，建议发布前人工一轮。
   以上 1/2 可直接脚本化进 `.docker/`（当前仓库已有 test/chain 两套 compose），本轮未执行
   （本机无 Docker/Linux tc 环境，Windows 宿主无法跑 netem）——**明确标注为待真实环境验证**。

## 2.5 结论汇总

| 项 | 结论 |
|---|---|
| 信任传递 | 逐跳验证 + E2E 端到端密钥解耦，无链式放大缺陷 |
| 降级混用 | 无跳级降级面；档位为签发属性，明文命中 e2e 组 fail-close |
| 路径操纵 | advertise 自报无验证（架构性，决策项）；无指标择路面故无指标欺骗面 |
| 共谋关联 | 明文档全可见；E2E 档留时序/长度元数据（已知取舍，抗关联需整形，决策项） |
| 重放/环路 | 信道内原有防护 ✓；跨信道重放 F1 已修；环路 F3 已修 |
| 跳数上限 | 8 跳 O(1) 快速拒绝 |
| 证书分发 | 无集中单点（逐节点 ACME/自签 + 设备密钥签名记录） |
| 性能 | RTT 近线性 +26µs/跳（回环）；吞吐 ×~0.8/跳；E2E 端点开销 0.4ns/B；mux 无队头阻塞 |
| 限速 | 单点计费无双跳压缩；双向合并语义文档化 |
