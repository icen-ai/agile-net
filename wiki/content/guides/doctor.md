# 自我诊断

自我诊断回答一个问题：**本机的 AgileNet 环境健不健康**。它把端口、系统代理、TUN、订阅内核、网络连通、配置数据、规则这七类最常见的问题来源逐项巡检，输出一份带状态的报告；能安全自动修复的项会当场修好，修不了的给出明确的手动处理指引。

两个入口，同一份报告：

- **CLI**：`anet doctor`（本机执行，无需 `anet login`、不读数据库、不写审计日志）
- **anet-gui**：设置 → 自我诊断，点击「开始诊断」生成报告；异常项附带处理按钮与说明

```bash
anet doctor            # 人类可读报告
anet doctor --json     # 结构化输出（{section, status, detail, fixed} 列表）
```

## 报告怎么看

报告按节（section）组织，每节对应一类检查，节内每项检查带一个状态：

| 状态 | 含义 | 需要做什么 |
| --- | --- | --- |
| 通过 | 检查项正常 | 无 |
| 提示 | 不影响运行的信息（如某可选能力未启用） | 按需关注 |
| 警告 | 当前可用但存在隐患（如端口被计划外进程占用过、规则有冗余） | 建议按指引处理 |
| 错误 | 已经影响功能（如系统代理残留、内核缺失） | 必须处理 |
| 已修复 | 发现过问题，诊断过程中已自动修复 | 确认修复说明即可 |

### 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 无错误（提示、警告与已修复不影响退出码） |
| `1` | 存在错误项，脚本可据此告警 |
| `2` | 用法或运行环境错误（参数非法、无权读取所需信息等） |

```bash
anet doctor --json || echo "环境存在异常，请查看报告"
```

## 端口与占用（ports）

**检查什么**：AgileNet 各角色需要的本地端口是否被计划外进程占用——客户端代理 `57890`、内嵌节点 API / Relay `59293` / `54431`；服务端角色开启时追加管理 API `59090` 与 Relay listener `54430`。

**正常表现**：端口空闲，或由 AgileNet 自己的进程（`anet-gui` / `anet-svc`）监听。

**常见异常与原因**：

- 端口被其他代理软件占用（Clash 系常用 7890/9090 段，AgileNet 默认全部落在 5 万段正是为了规避，但第三方软件仍可能撞上）。
- 上一次 AgileNet 异常退出，进程残留仍持有端口。

**自动修复**：无。端口归属涉及第三方进程，诊断只报告占用者（PID + 进程名），不代为结束进程。

**手动处理**：

```bash
# 任意平台（推荐，无需系统自带工具）
anet tool portof 57890

# Windows
netstat -ano | findstr 57890
tasklist | findstr <PID>

# macOS
lsof -i :57890

# 国产 Linux（麒麟 / UOS 裁剪镜像常缺 lsof）
ss -tlnp | grep 57890
```

确认占用者后：若是残留的 AgileNet 进程，结束它再启动；若是第三方软件，在设置中把 AgileNet 对应端口改到空闲端口（建议保持 5 万段）。

## 系统代理（sysproxy）

**检查什么**：系统代理开关状态与指向是否一致——开启时应指向本机 AgileNet 代理（`127.0.0.1:57890`）；关闭时系统代理应完全还原，不留残留。

**正常表现**：开关开 → 系统代理指向 AgileNet；开关关 → 系统代理为空或还原到开启前的原始值。

**常见异常与原因**：

- **残留**：AgileNet 进程被强杀（任务管理器结束、断电），来不及还原系统代理，导致系统代理指向一个已不存在的本地端口，表现为「全网断网」。
- **抢占**：Clash / FlClash / V2rayN 等其他代理软件在 AgileNet 之后改写了系统代理，AgileNet 的流量入口被截走，表现为「规则全部不生效」。

**自动修复**：检出**残留**时，将系统代理还原到 AgileNet 开启前备份的原始状态并标记「已修复」。检出**抢占**时不改动（那是其他软件的合法设置），只报告当前占用者。

**手动处理**：

- Windows：设置 → 网络和 Internet → 代理，核对「使用代理服务器」开关与地址。
- macOS：系统设置 → 网络 → 详细信息 → 代理，核对 Web 代理 / 安全 Web 代理 / SOCKS 代理三项。
- Linux：桌面环境网络设置中的代理页，或检查 `http_proxy` / `https_proxy` 环境变量。

**共存建议**：多台代理软件同时托管系统代理必然互相覆盖，只保留一个「系统代理的写者」。需要同时运行时，参考 [Clash / FlClash 共存](#/guides/clash)：AgileNet 走系统代理、另一台走规则订阅，或反之。若确认 AgileNet 是唯一写者，可在设置中开启「系统代理锁定」，被外部改写时自动抢回并提示。

## TUN 支持（tun）

**检查什么**：TUN 模式所需的系统能力是否就绪——虚拟网卡驱动可用、进程有创建 TUN 设备的权限。

**正常表现**：Windows 能找到可加载的 `wintun.dll`；macOS 可打开 `utun` 设备；Linux 存在 `/dev/net/tun` 且当前进程可写。

**常见异常与原因**：

- Windows：`wintun.dll` 缺失、被杀毒软件隔离，或版本过旧。
- macOS / Linux：权限不足（未以 root / 管理员运行）；国产 Linux 裁剪内核可能未编译 `tun` 模块，`/dev/net/tun` 不存在。

**自动修复**：无。驱动安装与提权必须由用户决策。

**手动处理**：

- Windows：从 [wintun.net](https://www.wintun.net) 下载对应架构的 `wintun.dll`，放到 `anet-gui.exe` 同目录（或安装目录的 `resources` 下），重新诊断。
- macOS：确认以授权方式启动（安装器已处理权限时无需操作）。
- Linux：检查 `ls -l /dev/net/tun`；缺失时 `sudo modprobe tun`，模块化内核裁剪机型需换装带 tun 的内核包；权限不足时以 root 运行或配置 capabilities。

TUN 不可用时不影响其他模式——退回系统代理 / 手动代理即可正常用，报告中该节为「提示」而非「错误」。

## 订阅内核（kernel）

**检查什么**：订阅代理内核（mihomo sidecar）二进制是否存在、版本是否匹配、进程状态是否健康，以及是否存在上次异常退出遗留的孤儿内核进程。

**正常表现**：内核文件在位、可执行、版本受支持；订阅代理开启时恰有一个内核子进程，父进程是 AgileNet。

**常见异常与原因**：

- **孤儿内核**：AgileNet 被强杀后内核子进程未被回收，继续持有混合端口与 API 端口，下次启动订阅代理报端口占用。
- **内核缺失或损坏**：下载被拦截、磁盘写坏、杀毒软件隔离。
- **版本不匹配**：手工替换过内核文件。

**自动修复**：检出孤儿内核时将其结束（仅认 AgileNet 启动参数特征的内核进程，不误伤用户自己装的 mihomo / Clash），并标记「已修复」。

**手动处理**：

- 内核缺失：在设置的订阅代理页重新下载内核；下载失败多为网络问题，先处理 network 节。
- 手工清理孤儿进程：Windows 用 `tasklist | findstr mihomo` 找到后 `taskkill /PID <PID> /F`；macOS / Linux 用 `pkill -f mihomo`。注意核对进程路径，勿误杀其他代理软件。

## 网络连通（network）

**检查什么**：分层验证本机出网能力——DNS 解析、到订阅更新地址的 TCP 连通、经本地代理的出口连通，输出「卡在哪一层」。

**正常表现**：三层全部连通，延迟在合理范围。

**常见异常与原因**：

- DNS 层失败：系统 DNS 被劫持或配置错误，或内网 DNS 不解析订阅域名。
- TCP 层失败：本机防火墙 / 网关拦截，或订阅地址本身不可达。
- 代理出口失败：本地代理未启动（客户端角色被关闭），或上游节点掉线。

**自动修复**：无。网络问题的原因在 AgileNet 之外，诊断只负责定位层级。

**手动处理**：

```bash
anet tool diag example.com 443     # 一键分层定位（DNS → ping → traceroute → tcping）
anet tool dns example.com          # 单独验证解析
anet tool tcping example.com 443   # 单独验证 TCP
```

按层级对症：DNS 失败先换系统 DNS 或检查 hosts；TCP 失败查防火墙（`anet tool fwstatus`）；代理出口失败回到 GUI 看节点连接状态。

## 配置与数据（config）

**检查什么**：AgileNet 配置文件与本地数据的可读性与完整性——TOML 能否解析、SQLite 数据库能否打开并通过完整性检查、关键字段是否在合法范围。

**正常表现**：全部文件可解析，数据库完整性检查通过。

**常见异常与原因**：

- 配置文件被手工编辑出语法错误，或从旧版本升级后字段失效。
- 数据库文件因断电 / 强杀损坏。

**自动修复**：检出**无法解析的配置文件**时，将原文件重命名为 `<文件名>.bak-<时间戳>` 备份，重建一份可启动的默认配置，并标记「已修复」。数据库损坏不自动重建（涉及凭据与审计数据），只报告并指引恢复路径。

**手动处理**：

- 配置与数据默认位于 `~/.agile-net/`（Windows 为 `%USERPROFILE%\.agile-net\`）。
- 自动重置后，从 `.bak` 文件把仍然有效的自定义段落（如端口、订阅链接）人工合并回新配置。
- 数据库损坏：停止 AgileNet 后从备份目录还原；无备份时删除库文件重新初始化，再从服务端重新登录拉取配置。

## 规则冲突（rules）

**检查什么**：当前生效规则集的健康度——用户规则与订阅规则是否互相覆盖、是否存在永不命中的冗余规则、是否有被暂停后遗忘的规则。

**正常表现**：规则按预期顺序生效，无大面积互相遮蔽。

**常见异常与原因**：

- 同一域名 / 网段被多条规则命中，排在前面的规则截胡（例如用户添加的 `direct` 规则盖住了订阅的代理规则）。
- 订阅更新后旧规则残留，与新规则语义冲突。
- 之前排查问题时暂停了规则，事后忘记恢复。

**自动修复**：无。规则取舍是用户意图，诊断只列出冲突对与被暂停清单。

**手动处理**：在 GUI 的「命中追踪」页输入目标域名，直接看到实际命中的是哪条规则、排在它前面的有哪些；据此调整顺序、删除冗余或在规则页恢复暂停项。命中追踪的完整用法见 [anet-gui 图形客户端](#/guides/gui)。

## FAQ：诊断全绿，但还是无法上网

报告全绿说明本机环境健康，问题在报告边界之外。按这个顺序排查：

1. **GUI 日志页 → 实时连接**：发起一次访问，看连接是否出现在列表里。
   - 完全看不到连接 → 流量根本没进 AgileNet，回到 sysproxy 节确认系统代理指向，或检查应用是否绕过了系统代理（部分应用需手动配置代理为 `127.0.0.1:57890`）。
   - 能看到连接但立刻关闭（红色）→ 看出错信息，多为上游节点或 TLS 问题，转 [故障排查与诊断](#/guides/troubleshooting)。
2. **命中追踪**：输入目标域名，确认命中的是预期的规则与链路（出口节点是否正确）。命中了 `direct` 或错误链路 → 回到 rules 节处理冲突。
3. **doctor 报告 network 节**：确认三层连通里「经本地代理的出口」一项真实通过；该项为提示状态时，用 `anet tool bandwidth` 实测到上游的隧道吞吐，排除「能连上但跑不动」的链路劣化。
4. 以上都正常仍不通 → 问题在目标站点或对端网络，用 `anet tool diag <目标域名> 443` 做最后一层定位。
